# What Changed for a Project That Already Uses This Skill

Read by the upgrade route ([upgrade-project.md](upgrade-project.md)), after the new version is installed.
One row per release since 3.37.0, because a project that came before has no other way to learn what its next run
does differently from the last one: most changes below take effect **without anyone touching
`docs/process/pipeline.json`**, and a few of them move a guarantee. `CHANGELOG.md` has the evidence behind each
row; this file has only what the person upgrading has to be told, in their language.

## How to use it

1. The version the project came from is in the header of `## Status` ("Regenerated by spec-driven-roadmap
   v3.36.0 …"). The version now on disk is in `SKILL.md`. Use the rows **after the first and up to the second**,
   inclusive of the second.
2. For each such row, say its **Changes by itself** column in two sentences at most. A row whose column **begins
   with `Nothing:`** only states what stays the same: skip it. Every other row describes a change and is told, even
   when it adds that there is nothing to decide, because the person can still be surprised by it. A row dated after
   the version on disk is not in range.
3. For each **new key** the project's `pipeline.json` lacks, in **any** row in range — also in a row skipped in
   step 2, whose keys are still new to this project — offer it **once** when the condition written in that row holds
   (if you cannot measure the condition, say so and offer it with the condition), with the price Step 10 of [handover-prompt.md](handover-prompt.md) states for it. Write a value into
   `pipeline.json` only after the person says yes to that key. `"confirmed"`, `"mergeGate"` and
   `"verifier.survivor"` are theirs alone: never write them on your own initiative.
4. Run `python3 <this-skill-dir>/scripts/plan-pipeline.py --root <project-root> --check-config` and report every
   problem it names, with the row that explains it. It changes nothing; besides the file it reads which downstream skill
   is installed, whether the main branch it names exists, and whether the scripts the config runs are in the project.


## The rows

| Version | Changes by itself, in a project that does not touch its config | New optional keys of `pipeline.json` |
|---|---|---|
| 3.37.0 | A builder waits for what it starts (a test batch, a lock regeneration) instead of ending its attempt with a background job running. Nothing to decide. | none |
| 3.38.0 | Nothing: the full gate still runs before the verifier. | `gateOrder`: `gate-first` (today's behaviour) or `verify-first`. Offer `verify-first` only when the gate is long beside a verification (`bench-gate.py` times it). |
| 3.39.0 | **Verifications after the first are scoped** to the rows the last report did not pass and to what changed since, instead of a fresh sweep each time. The price: a loose first round leaves its loose PASS rows standing. What is noticed outside the scope is a `minor` issue (3.43.1 changes that: see its row). | `verifier`: `sensor` (a cap of mutants per tier), `survivor` (`minor` only under `tlc-spec-driven`), `rounds` (`scoped` is the default; `full` turns the scoping off). Offer `rounds: "full"` to anyone who prefers to re-verify everything. |
| 3.40.0 | **Manager mode only:** an existing test is updated, not obeyed, when the feature's own spec changes what it asserts. Each is a commit whose first line is `REVOKED-TEST`; the person reviews them with `git log main --grep=REVOKED-TEST`. | none |
| 3.41.0 | A key under `manager` that nothing reads is refused instead of ignored (a project's `manager.passes` is the known case: a second pass would restart every feature at attempt 1, so delete it and raise the top-level `maxAttempts`, whose default is A 5, B 4, C 3). | `models`: a model per role (Infinity-Agent-Creator had it in a locally patched copy of the skill; this is its home). Offer when the whole pipeline runs on one model and the person wants a stronger one for `build` and `verify`. |
| 3.42.0 | `measure-agents.py` also reports time: wall-clock by role, how many agents ran at once, verifications passed or refused. A baseline saved before 3.42.0 has no time in it: compare with it first, then save a new one, and time can be compared from then on. | none |
| 3.43.0 | Nothing: the merge still runs the gate again. | `mergeGate`: `rerun` (today's behaviour) or `receipt`, which needs a `barrierGate` and a `barrierEvery` of at least 1. Offer it only to a project that already has a barrier. |
| 3.43.1 | Corrections: the receipt records the commit the tree was built on, a verification is a later round only when a report exists, the criterion behind a test correction must predate the branch. A defect noticed outside a scoped round keeps its true severity again (3.39.0 made it `minor`); only a weakness that is not a defect is `minor`. A `pipeline.json` that 3.43.0 accepted can now be refused: `lanes` 0, an unknown key inside `verifier` or `manager.effort`. Nothing to decide. | none |
| 3.44.0 | **`pipeline.json` keys that nothing reads are refused**, naming the key: a setting that existed only in a locally patched copy of the skill is no longer silently ignored. `postMerge` (a command run once on the main branch after each merge, such as a database migration) is now part of the skill. | `postMerge`. If the project has a local patch that runs something after each merge, this is its home. |
| 3.45.0 | The installer has `--check` and `--diff` (what would an install replace, which files of the installed copy the project changed and what they changed), `plan-pipeline.py --check-config` validates the config without planning and warns about a script the config runs that is not in the project, and this file exists. Nothing to decide. | none |
| 3.46.0 | A builder's first attempt on a branch that already exists (an earlier run built on it) rebases it onto the main branch itself and resolves the conflict, instead of leaving it to the prover, which fixes nothing and can spend an attempt on it (3.47.0 changes how: see its row). `measure-agents.py` also prints which stage the refusals came from (builder not finished, prover refused, reviewer blocker or major, merge failed). A project that ran a second pass per section (`manager.passes`) gets the same room from a higher top-level `maxAttempts`. Nothing to decide. | none |
| 3.47.0 | **Manager mode:** a planner reply that cannot be used is tried again, up to three tries in all, and a block names what was missing. **Every pipeline:** a builder, prover or merger brings the main branch in by nothing when the branch already holds it, a merge when the branch has merges of its own and a rebase only for a linear branch (this replaces 3.46.0's rebase), and a builder **stops with `ready=false`** on a conflict in an existing test that the feature and the main branch both changed, instead of settling it. `check-roadmap.py` flags a section slugged `history` or `index`, or two files in `docs/` that differ only by case (a failure in 3.47.0, a warning from 3.48.0: see its row); if a section is slugged that way, decide whether to rename it before its features are built. The test stop costs an attempt per builder until the feature is blocked, with the test named. | none |
| 3.48.0 | Corrections from a full review: a verifier that says pass while listing an unmet criterion is **refused**, not merged; the manager reads the child's feature lines exactly (a test named `…skipped…` no longer blocks a section) and **stops** after a failed post-merge command; a planner reply for another section, or one that dropped a key, is tried again; a `maxAttempts` that names one tier keeps the defaults for the others; the triage probe names the right feature after a branch took the main branch by a merge; the prover and the merger undo a conflicted rebase or merge instead of leaving it, and name the feature branch; with one lane, a builder stashes what an earlier agent left in the shared tree (never the installed skills, `docs` or `.specs`), says so in the account, and commits before it replies; the triage merger keeps a merged repair merged and undoes a conflicted rebase; the triage probe classifies a failing test the batch itself added; the prover deletes a gate-failure note once the gate passes; the tier A reviewer is given the notes it is told to spot-check; the merger no longer reports a failed merge after the main branch moved; a scoped verification covers the feature's own files; `check-roadmap.py`'s case check is a **warning** again (as a failure it blocked manager mode's decomposer); the planner and `--check-config` refuse a non-boolean `confirmed` or `push`, an empty `gate` or `model`, a `waitChunk` that is not a whole number and a `featureStatus` that is not `done` or `build` — **a `pipeline.json` that 3.47.0 accepted can now be refused**: run `--check-config` and fix each line (a `push: "no"` pushed under 3.47.0); `--check-config` also checks that the main branch exists. With `push: true`, a failed push is marked on the feature's line; what a builder stashed is said in the account. | none |
| 3.49.0 | The verifier and the reviewer are told they edit no test and no code (manager mode gave them the builder's rule for correcting a test); manager mode reads the run's own `barrier`, `triage` and `stashed` lines by their exact shape, so a feature with one of those names is no longer mistaken for them. Nothing to decide. | none |

Releases before 3.37.0 are not in this table. A project older than that is brought up to date by the route in
[upgrade-project.md](upgrade-project.md) all the same; read `CHANGELOG.md` from the project's version for what it
skipped.
